# Plugin Architecture

Native plugins extend ChronoSys with AI tools and user commands. They run in-process in agent-host and are gated only by a global enable toggle and per-tool Persona blacklists.

## 1. Plugin kinds (implemented)

| Kind | Role | Status |
|------|------|--------|
| `tool` | AI-callable function registered as `AgentTool` | ✅ |
| `command` | User-facing `/command` executed directly | ✅ |

Future: `adapter`, `skill`, `hook`, `runtime`.

## 2. Package layout

```text
my-plugin/
├── chrono.plugin.toml    # required manifest
├── chrono.policy.toml    # generated by WebUI, checked into VCS for defaults
├── tools/
│   └── index.ts          # agent-host native entry
└── assets/
```

Install path (single version per plugin ID):

```text
$CHRONO_HOME/plugins/installed/<plugin-id>/
```

## 3. Manifest (`chrono.plugin.toml`)

```toml
id = "test.full"
name = "Full Test Suite"
version = "1.0.0"
chrono_api = "1"
description = "Exercises every native plugin feature."

[entry]
tools = ["tools/index.ts"]
commands = ["tools/index.ts"]

# Each [[tools]] / [[commands]] row MUST match exactly one registerTool / registerCommand
# in the JS entry files. Mismatch → load_error.
[[tools]]
name = "test.echo"
label = "Test Echo"
description = "Returns the input text prefixed with the configured greeting."

[[commands]]
name = "test_status"
label = "Test Status"
description = "Reply with plugin version and entry counts."

# Config fields rendered as Input (string) or Toggle (boolean) in the WebUI editor.
[[config]]
key = "greeting"
label = "Greeting"
type = "string"
default = "Hello"
description = "Prepended to echo output."
```

Field rules:

- `id`: `^[a-z][a-z0-9]*(?:[._-][a-z0-9]+)*$`
- `version`: SemVer `major.minor.patch`
- `chrono_api`: must be `"1"`
- Tool/command `name`: `^[a-z][a-z0-9_.-]{0,63}$`; for Telegram menu visibility use only `[a-z0-9_]`
- `[[config]]` keys appear in plugin config page; `type` is `"string"` or `"boolean"`
- `[[tools]]` and `[[commands]]` are authoritative for name/label/description; JS code only provides `execute()`

## 4. Native entry (`tools/index.ts`)

```ts
export default function register(api: {
  Type: typeof import("@earendil-works/pi-ai").Type;
  registerTool(d: unknown): void;
  registerCommand(d: unknown): void;
}) {
  api.registerTool({
    name: "test.echo",                        // must match manifest [[tools]]
    label: "Test Echo",
    description: "Returns the input text prefixed with the configured greeting.",
    parameters: api.Type.Object({ text: api.Type.String() }),
    async execute(_id, params, _signal, _onUpdate, ctx) {
      const greeting = String(ctx.config["greeting"] ?? "Hello");
      return { content: [{ type: "text", text: `${greeting}, ${params.text}` }] };
    },
  });

  api.registerCommand({
    name: "test_status",                      // must match manifest [[commands]]
    label: "Test Status",
    description: "Reply with plugin version.",
    async execute(_id, _args, ctx) {
      await ctx.platform.send({ text: "v1.0.0 — all systems nominal." });
    },
  });
}
```

`ctx` provides:

- `ctx.config` — values from `chrono.policy.toml [config]`
- `ctx.platform.send({ text, chatId? })` — send a message through the bound platform adapter
- `ctx.pluginId`, `ctx.sessionKey` — runtime metadata

No raw `fs`, `child_process`, network, or filesystem access.

## 5. Policy (`chrono.policy.toml`)

```toml
enabled = true

[config]
greeting = "Hello"
verbose = false

[tools."test.echo"]
persona_blacklist = ["persona-blocked"]
```

- `enabled` — global on/off; disabled plugins show their tools/commands from manifest metadata without loading JS
- `[config]` — plugin-defined key-value pairs; edited in WebUI plugin editor
- `[tools."<name>"]` — per-tool Persona blacklist; managed in Persona editor's Tools modal

Agent-host prunes stale Persona IDs from blacklists on every `config.reload`.

## 6. Discovery & validation

On reload, agent-host:

1. Scans `$CHRONO_HOME/plugins/installed/` — each subdirectory is one candidate
2. Parses `chrono.plugin.toml` → manifest (id, metadata, config schema, entry paths)
3. Reads `chrono.policy.toml` → policy (enabled, config values, persona blacklists)
4. If **disabled**: builds view from manifest metadata only (no JS loading)
5. If **enabled**: dynamic `import()` of entry files → executes `register()` → cross-validates:
   - JS-registered names must all appear in manifest `[[tools]]` / `[[commands]]`
   - All manifest-declared names must have a corresponding JS registration
   - Mismatch → `load_error`, plugin unavailable
6. View uses manifest metadata as authoritative source for name/label/description

Duplicate plugin IDs across directories → `duplicate_id`.

## 7. Persona integration

- Plugin tools are NOT in Persona `tools_allowlist_json` — they are controled by the plugin's per-tool blacklist
- Persona editor's Tools modal shows every plugin tool with a toggle
- Toggling a plugin tool OFF for a Persona writes that Persona ID into the tool's `persona_blacklist`
- When constructing `AgentTool[]` for a turn, agent-host passes the current `personaId`; blacklisted tools are omitted

## 8. Command registration with platforms

After `config.reload` or plugin reload, agent-host sends `host_command_sync` to gateway with all enabled command names and descriptions. The Telegram adapter merges built-in commands (`/new`, `/compact`) with plugin commands and calls `setMyCommands`. Command names containing characters outside `[a-z0-9_]` are silently filtered (Telegram restriction).

## 9. WebUI surfaces

| Page | Purpose |
|------|---------|
| Extensions list (`/plugins/extensions`) | Discover, enable/disable, delete, install ZIP or GitHub |
| Plugin editor (`/plugins/extensions/:id`) | View registered entries, edit config, disabled notice |
| Persona editor Tools modal | Toggle plugin tool visibility per persona |

## 10. Installation

- **ZIP upload**: `POST /api/v1/plugins/install/zip` — ≤20 MiB, ≤512 entries, ≤50 MiB extracted, path traversal rejected
- **GitHub**: `POST /api/v1/plugins/install/github` — accepts only `https://github.com/owner/repo`, optional `git_ref` (tag/branch), shallow clone
- **Delete**: `DELETE /api/v1/plugins/{id}/policy` — removes plugin directory and reloads

## 11. Compatibility boundary

Pi coding-agent extensions (`pi-web-access` etc.) use `ExtensionAPI`, not Chrono's native registration. They are not discovered, installed, or executed by the native loader. A future adapter must live in a separate boundary and map Pi's registration to Chrono's `AgentTool[]` contract.

## 12. Development guide

### Creating a plugin

1. Create directory: `$CHRONO_HOME/plugins/installed/<plugin-id>/`
2. Add `chrono.plugin.toml` with id, name, version, `[[tools]]`/`[[commands]]` metadata, `[[config]]` schema, and `[entry]` paths
3. Add `chrono.policy.toml` with `enabled = true` and any `[config]` defaults
4. Implement `tools/index.ts` with `export default function register(api)`
5. Restart gateway or click **Refresh** in Extensions list
6. Verify in plugin editor: all registered entries and config fields should appear

### Testing without a platform

```bash
cd agent-host
bun test src/plugins.test.ts
```

The test suite uses fixtures under `__fixtures__/` that are copied to temp directories.

### Debugging

- Plugin status and errors appear in the plugin editor (red border with message)
- Gateway logs `[telegram] syncing N bot commands` / `synced N commands` for command sync
- Gateway logs `[gateway] syncing commands to N adapter(s)` when receiving `host_command_sync`
- Agent-host stderr shows `host_warn` for unknown tool names in allowlists
